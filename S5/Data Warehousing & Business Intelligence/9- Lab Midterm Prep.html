1OLTP vs DSS vs DW

Lab 01 — Understanding the two worlds of data systems

Every database serves a purpose. OLTP (Online Transaction Processing) keeps day-to-day business running; a DSS/DW (Decision Support System / Data Warehouse) helps managers decide. They are built differently on purpose.

Definition
OLTP: Optimised for high-speed, row-level INSERT/UPDATE/DELETE operations. One transaction at a time. Normalised schema to protect consistency.
Definition
DSS / Data Warehouse: Optimised for aggregation across millions of rows. Read-heavy, historical. Answers "Which region drove the most revenue this quarter?"

Key Comparison

DimensionOLTPDSS / DW
Primary operationINSERT / UPDATE / DELETESELECT + GROUP BY / aggregates
Query typePoint lookup — "Order 104512?"Aggregation — "Revenue by region?"
Schema styleNormalised (3NF)Denormalised star/snowflake
Data currencyCurrent (real-time)Historical (periodic loads)
Typical usersClerks, operational staffManagers, analysts, BI tools
Rows per query1–10 rowsMillions of rows
Performance concernWrite throughput, concurrencyRead speed, aggregation performance

Role of DW/BI in Decision-Making

  • Single source of truth — one consistent version of business data across systems
  • Historical context — compare this quarter to last year
  • Cross-system integration — sales + inventory + HR in one place
  • Self-service analytics — managers answer questions without IT involvement
Example

CampusCart: Two Query Worlds

-- OLTP: point lookup — retrieve one specific order
SELECT * FROM lab01.campuscart_sales WHERE order_id = 104250;

-- DSS: aggregation across 7,800 rows
SELECT date_trunc('month', order_date) AS month,
       category,
       SUM(net_revenue_pkr) AS net_revenue
FROM   lab01.campuscart_sales
WHERE  order_status <> 'Cancelled'
GROUP  BY 1, 2
ORDER  BY 1, net_revenue DESC;
Exam Tip
EXPLAIN ANALYZE: OLTP point-lookup → Index Scan (fast, few rows). DSS aggregate → Sequential Scan + HashAggregate (scans everything). You may be asked to identify which is OLTP vs DSS from the plan.

Key Takeaways

  • OLTP = fast writes, current data, normalised, point lookups
  • DSS = fast reads, historical, aggregation, millions of rows
  • DW is the foundation for BI — consolidates, cleans, and stores history
  • Same dataset → very different query patterns depending on the question
Practice Questions
Easy: Give two differences between OLTP and DSS systems.

Answer: (1) OLTP is optimised for INSERT/UPDATE/DELETE on individual rows; DSS is optimised for SELECT aggregations across millions of rows. (2) OLTP stores current data; DSS stores historical data over time.

Medium: "Which product category had the highest return count last month?" — OLTP or DSS query? Why?

Answer: DSS. It scans all order rows for last month, filters by order_status='Returned', groups by category, and counts — a classic aggregation query, not a point lookup.

Hard: Why is running DSS queries directly on an OLTP production database problematic?

Answer: DSS queries do full-table scans and hold locks for long durations, competing with the constant INSERT/UPDATE stream on OLTP — causing lock contention, degraded write performance, and slower response for operational users. The normalised schema also requires many joins, making analytical queries slow. A separate DW with denormalised schema and read-only access eliminates these problems.

2PostgreSQL Basics

Lab 01 — DDL: databases, schemas, tables, data types, PKs, FKs

PostgreSQL organises objects in a three-level hierarchy: Database → Schema → Table. Schemas are namespaces — lab01 and lab03 can coexist in the same database without name conflicts.

Example

Complete Lab Setup Workflow

-- 1. Create schema (namespace)
CREATE SCHEMA IF NOT EXISTS lab01;

-- 2. Create table inside schema
CREATE TABLE lab01.campuscart_sales (
    order_id          INT,
    order_date        DATE,
    customer_id       INT,
    customer_segment  TEXT,
    product_id        INT,
    product_name      TEXT,
    category          TEXT,
    region_id         TEXT,
    channel           TEXT,
    quantity          INT,
    unit_price_pkr    NUMERIC(12,2),   -- NUMERIC for money, never FLOAT!
    discount_pct      INT,
    order_status      TEXT,
    gross_revenue_pkr NUMERIC(14,2),
    net_revenue_pkr   NUMERIC(14,2)
);

-- 3. Manual insert
INSERT INTO lab01.campuscart_sales (order_id, order_date, category, net_revenue_pkr)
VALUES (9999, '2025-03-15', 'Electronics', 4500.00);

-- 4. Import CSV: pgAdmin → right-click table → Import/Export Data
--    Settings: Header=Yes, Delimiter=comma, Encoding=UTF-8

Primary Keys & Foreign Keys

Definition
Primary Key (PK): Uniquely identifies every row. Cannot be NULL. Example: order_id INT PRIMARY KEY.
Definition
Foreign Key (FK): References the PK of another table. Enforces referential integrity — prevents orphan rows. Example: product_id INT REFERENCES products(product_id).
Example

PK + FK in Practice

CREATE TABLE products (
    product_id   INT PRIMARY KEY,
    product_name TEXT,
    category     TEXT
);

CREATE TABLE order_items (
    line_id    INT PRIMARY KEY,
    order_id   INT,
    product_id INT REFERENCES products(product_id),  -- FK
    quantity   INT
);
Common Mistake
Confusing schemas and databases. A schema is a namespace inside one database (like a folder). A database is a separate server-level container. Labs use one database + multiple schemas.

Key Takeaways

  • Hierarchy: CREATE DATABASE → CREATE SCHEMA → CREATE TABLE
  • Use NUMERIC(p,s) for money — never FLOAT (causes rounding errors)
  • PKs enforce uniqueness; FKs enforce referential integrity
  • Import CSVs: pgAdmin → right-click table → Import/Export Data
Practice Questions
Easy: What is a schema in PostgreSQL?

Answer: A namespace/container within a database that groups related tables. Example: lab03 for normalised tables and lab03_report for reporting tables — both in the same database, logically separated.

Medium: Write DDL for a Customers table: customer_id, name, segment, registration_date.

Answer:

CREATE TABLE customers (
    customer_id       INT PRIMARY KEY,
    name              TEXT,
    segment           TEXT,
    registration_date DATE
);

Hard: order_items has a FK on product_id. Developer tries to INSERT a row with product_id=999 that doesn't exist in products. What happens?

Answer: PostgreSQL raises a foreign key violation error and rejects the INSERT. The FK constraint verifies product_id=999 exists in products before allowing the row — referential integrity enforcement. Fix: insert the product first, or the FK is wrongly pointing to the wrong table.

3Analytical SQL

Labs 01 & 04 — SELECT, aggregations, GROUP BY, HAVING, JOINs, Top-N, trend analysis

Mental model for analytical SQL: filter rows → group rows → aggregate → filter groups → sort/present. This maps exactly to: WHERE → GROUP BY → aggregate functions → HAVING → ORDER BY.

Example

All Clauses Together — The Complete Query

SELECT
    category,
    channel,
    COUNT(*)                  AS order_count,
    SUM(net_revenue_pkr)      AS total_revenue,
    AVG(net_revenue_pkr)      AS avg_revenue,
    MIN(net_revenue_pkr)      AS min_revenue,
    MAX(net_revenue_pkr)      AS max_revenue
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'          -- row-level filter (BEFORE grouping)
GROUP  BY category, channel                -- collapse rows into groups
HAVING SUM(net_revenue_pkr) > 1000000     -- group-level filter (AFTER aggregation)
ORDER  BY total_revenue DESC               -- sort output
LIMIT  5;                                  -- top-N

Key Clauses Reference

ClausePurposeKey Rule
WHEREFilter rows before groupingCannot reference aggregate functions
GROUP BYCollapse rows by distinct valuesEvery non-aggregate in SELECT must be here
HAVINGFilter groups after aggregationUse when condition involves SUM, COUNT, etc.
ORDER BYSort resultDESC = largest first; ASC = default
DISTINCTRemove duplicate rowsSELECT DISTINCT category FROM …
LIMITReturn only N rowsUse AFTER ORDER BY for Top-N

Top-N Queries

Example
-- ALWAYS aggregate first, THEN limit
SELECT product_name, category,
       SUM(net_revenue_pkr) AS total_revenue
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'
GROUP  BY product_name, category
ORDER  BY total_revenue DESC
LIMIT  5;   -- Top 5 products

Trend Analysis (Monthly)

Example
-- date_trunc truncates date to given precision
SELECT date_trunc('month', order_date) AS month,
       SUM(net_revenue_pkr)            AS monthly_revenue,
       COUNT(DISTINCT order_id)        AS orders
FROM   lab01.campuscart_sales
WHERE  order_status <> 'Cancelled'
GROUP  BY 1          -- "1" refers to first SELECT column
ORDER  BY 1;         -- chronological order

JOINs

Definition
INNER JOIN: Returns only rows where the condition matches in both tables. Unmatched rows excluded from both sides.
Definition
LEFT JOIN: Returns ALL rows from the left table + matched rows from the right. Unmatched right-side columns are NULL. Use for orphan detection.
Example

INNER JOIN vs LEFT JOIN + Orphan Detection

-- INNER JOIN: only items with a matching product
SELECT oi.line_id, p.product_name, oi.quantity
FROM   order_items oi
INNER JOIN products p ON oi.product_id = p.product_id;

-- LEFT JOIN: all items; NULL product_name = orphan
SELECT oi.line_id, p.product_name
FROM   order_items oi
LEFT  JOIN products p ON oi.product_id = p.product_id;

-- Orphan detection pattern:
SELECT oi.line_id
FROM   order_items oi
LEFT  JOIN products p ON oi.product_id = p.product_id
WHERE  p.product_id IS NULL;   -- these items have no matching product
Exam Tip — HAVING vs WHERE
The #1 exam trap. Use WHERE order_status = 'Completed' (row filter). Use HAVING SUM(revenue) > 1000000 (group filter). You cannot write WHERE SUM(...) > ... — it's a syntax error.
Common Mistake
Top-N before aggregating. Always: GROUP BY → ORDER BY DESC → LIMIT. If LIMIT comes before GROUP BY, you get raw top rows, not the top aggregated groups.

Key Takeaways

  • Execution order: WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  • SUM, AVG, COUNT, MIN, MAX — collapse multiple rows into one value per group
  • INNER JOIN = intersection only; LEFT JOIN = all left + matched right (NULLs for misses)
  • Top-N = GROUP BY + ORDER BY DESC + LIMIT — always this order
  • Trend: date_trunc('month', date_col) groups all days in a month together
Practice Questions
Easy: Write a query for total net revenue and order count per channel, completed orders only.

Answer:

SELECT channel,
       SUM(net_revenue_pkr) AS total_revenue,
       COUNT(*)             AS order_lines
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'
GROUP  BY channel
ORDER  BY total_revenue DESC;

Medium: Return customer segments where avg order-line revenue exceeds PKR 5,000, completed orders only.

Answer:

SELECT customer_segment,
       AVG(net_revenue_pkr) AS avg_revenue
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'
GROUP  BY customer_segment
HAVING AVG(net_revenue_pkr) > 5000
ORDER  BY avg_revenue DESC;

Hard: Top 3 region+category combinations by net revenue, only combinations with more than 100 orders.

Answer:

SELECT region_name, category,
       SUM(net_revenue_pkr) AS total_revenue,
       COUNT(*)             AS order_count
FROM   lab01.campuscart_sales
WHERE  order_status <> 'Cancelled'
GROUP  BY region_name, category
HAVING COUNT(*) > 100
ORDER  BY total_revenue DESC
LIMIT  3;

Power Query — Data Cleaning

Definition
Power Query: The ETL layer inside Power BI. Apply transformations (change types, rename columns, filter rows, remove duplicates) before data enters the model. All steps auto-replay on refresh.
  • Set correct data types: IDs → Whole Number, dates → Date, money → Decimal Number
  • Rename queries: Sales, Products, Regions (not "Query1")
  • Check for blanks in key columns, inconsistent casing in text columns
  • Verify row counts match expected values after import

Data Model & Relationships

Definition
One-to-Many (1:*): "1" side (dimension) has unique keys; "*" side (fact) has repeated FK values. Filters flow 1→* by default (single cross-filter direction).
Example
-- Lab 02 Model:
Products[product_id]  1 ──────── * Sales[product_id]
Regions[region_id]   1 ──────── * Sales[region_id]

Rules:
• "1" side key must be UNIQUE and NOT NULL
• Create in Model View: drag a column onto the related column
• Use single cross-filter direction (lookup → fact)

Example

Units Sold          = SUM(Sales[quantity])

  • CSV: Get Data → Text/CSV | PostgreSQL: Get Data → PostgreSQL

Practice Questions
Easy: What is a slicer? How does it differ from the Filters pane?

Answer: A slicer is an on-canvas visual element users click to interactively filter page visuals. The Filters pane is behind-the-scenes — developers set static/dynamic filters there. Slicers are user-facing and always visible; Filters pane entries can be hidden.

Medium: Power BI won't create a 1:* relationship between Products[product_id] and Sales[product_id]. Likely cause and fix?

Answer: Products table has duplicate product_id values (or NULLs). Fix: Power Query → Remove Duplicates on product_id, or investigate the source. The "1" side must have unique, non-null keys.

Hard: What is "filter context" in Power BI? How does the same measure show different values in a card vs a bar chart?

Answer: Filter context = the set of active filters Power BI applies when evaluating a measure. In a card with no slicers, all rows are visible → grand total. In a bar chart with Category on the axis, each bar creates its own filter context ("Electronics only", "Stationery only", etc.) — the same SUM formula evaluates only those rows. The formula is identical; the data it sees changes with context.

5Normalization & Denormalization

Lab 03 — Logical vs physical models, 3NF, pre-join, column replication, pre-aggregation

Normalization reduces redundancy and prevents inconsistency. Denormalization deliberately adds redundancy for analytical performance. Both are valid — the key is knowing when to use each.

Definition
Logical Data Model: Describes what data exists — entities, attributes, relationships, and business rules. Technology-independent ERD with PKs, FKs, and cardinalities.
Definition
Physical Data Model: Describes how data is stored — actual table names, column types, indexes, and constraints for a specific DBMS (PostgreSQL). Translates the logical model into runnable DDL.

Why Normalize? The Three Anomalies

A wide flat table (like the CampusCart CSV) stores product name, category, region name on thousands of rows — creating:

  • Update anomaly: Rename "Electronics" → must update thousands of rows. Miss one → inconsistency.
  • Insert anomaly: Can't add a product without also having a sale.
  • Delete anomaly: Delete the last sale of a product → lose the product's details forever.
Example

Lab 03: Normalised Schema (3NF)

CREATE TABLE lab03.regions (
    region_id TEXT PRIMARY KEY, region_name TEXT);

CREATE TABLE lab03.customers (
    customer_id INT PRIMARY KEY,
    customer_name TEXT, customer_segment TEXT);

CREATE TABLE lab03.products (
    product_id INT PRIMARY KEY,
    product_name TEXT, category TEXT, brand TEXT);

CREATE TABLE lab03.orders (
    order_id INT PRIMARY KEY,
    order_date DATE,
    customer_id INT REFERENCES lab03.customers(customer_id),
    region_id   TEXT REFERENCES lab03.regions(region_id),
    channel TEXT, payment_method TEXT, order_status TEXT);

CREATE TABLE lab03.order_items (
    line_id INT PRIMARY KEY,
    order_id   INT REFERENCES lab03.orders(order_id),
    product_id INT REFERENCES lab03.products(product_id),
    quantity INT, unit_price_pkr NUMERIC(12,2),
    discount_pct INT, net_revenue_pkr NUMERIC(14,2));

-- Load dimensions from flat source using DISTINCT
INSERT INTO lab03.regions
SELECT DISTINCT region_id, region_name FROM lab03.raw_sales_flat;

INSERT INTO lab03.customers
SELECT DISTINCT customer_id, customer_name, customer_segment
FROM   lab03.raw_sales_flat;

Three Denormalization Strategies

Definition
1. Pre-Join Denormalization: Materialise all joins into one wide reporting table. Query reads one table instead of 4–5 joins at runtime. Trade-off: data duplication, must refresh when sources change.
Example
CREATE SCHEMA lab03_report;

CREATE TABLE lab03_report.sales_prejoined AS
SELECT oi.line_id, o.order_id, o.order_date,
       c.customer_segment, r.region_name,
       p.product_name, p.category, p.brand,
       o.channel, oi.quantity, oi.net_revenue_pkr
FROM   lab03.order_items oi
JOIN   lab03.orders    o ON oi.order_id   = o.order_id
JOIN   lab03.customers c ON o.customer_id = c.customer_id
JOIN   lab03.regions   r ON o.region_id   = r.region_id
JOIN   lab03.products  p ON oi.product_id = p.product_id;
Definition
2. Column Replication / Movement: Copy frequently-filtered attributes (e.g., customer_segment, region_name) into another table (Orders) to avoid joins at query time. Risk: stale if master changes.
Definition
3. Pre-Aggregation: Compute and store summary totals in advance. Repetitive executive dashboards hit a tiny summary table instead of millions of detail rows.
Example
CREATE TABLE lab03_report.monthly_region_category AS
SELECT DATE_TRUNC('month', o.order_date) AS reporting_month,
       r.region_name, p.category,
       SUM(oi.net_revenue_pkr)    AS total_net_revenue,
       SUM(oi.quantity)           AS total_quantity,
       COUNT(DISTINCT o.order_id) AS distinct_orders
FROM   lab03.order_items oi
JOIN   lab03.orders   o ON oi.order_id  = o.order_id
JOIN   lab03.regions  r ON o.region_id  = r.region_id
JOIN   lab03.products p ON oi.product_id= p.product_id
WHERE  o.order_status = 'Completed'
GROUP  BY 1, 2, 3;
-- Result: tiny table (12 mo × N regions × M categories) — instant queries

Design Selection Guide

WorkloadBest DesignReason
Live order updates, frequent writesNormalised (3NF)Updates one place, no anomalies
Executive repeating dashboardPre-AggregatedTiny summary table, instant
Analyst exploring raw detailPre-JoinedOne fat table, no joins needed
Region rename must be consistentNormalisedChange one row in Regions table

Key Takeaways

  • Logical = what data (ERD, tech-agnostic); Physical = how stored (DDL for a specific DBMS)
  • Normalization eliminates redundancy → prevents update/insert/delete anomalies
  • Pre-join: one fat table, no runtime joins — good for exploratory analysis
  • Column replication: copies attributes for fast filtering — risk is staleness
  • Pre-aggregation: tiny summary table for repetitive reporting — fastest for dashboards
Practice Questions
Easy: What is an update anomaly? Example using a flat sales table.

Answer: Changing one logical fact requires updating many rows. Example: renaming region "East Lahore" in a flat table requires updating 2,000 rows. Miss 500 → inconsistency. A normalised model stores it once in Regions — one row to update.

Medium: Compare pre-join denormalization and pre-aggregation. When would you use each?

Answer: Pre-join creates a wide table at detail grain (all attributes joined). Use for exploratory analysis needing raw rows with many attributes. Pre-aggregation computes totals at summary grain. Use for repetitive executive dashboards querying the same GROUP BY daily. Pre-aggregation is faster for summaries; pre-join is more flexible but still holds all detail.

Hard: Developer copies region_name into Orders table (column replication). "North Zone" is later renamed to "Northern Zone" in Regions. What problem arises?

Answer: Orders still shows "North Zone" while Regions shows "Northern Zone". Reports querying Orders get the old name; reports joining Regions get the new name — inconsistency. A normalised design stores only region_id in Orders and joins to Regions for the name. One update to Regions propagates everywhere automatically.

6Dimensional Modeling

Lab 05 — Star schema, fact/dimension tables, grain, measures, natural/surrogate keys

Dimensional modeling organises data for analytics. It answers: "What happened, when, where, by whom, involving what?" The result is a star schema — one central fact table surrounded by dimension tables.

Definition
Business Process: The analytical subject being modelled. One fact table per business process. Examples: Sales Transactions, Inventory Snapshots, Promotions.
Definition
Grain: Precise description of what one row in the fact table represents. Must be declared BEFORE building anything else. Example: "One row in FactSales = one order-line item for one product."
Definition
Fact Table: Central table. Contains numeric measures (quantities, revenues) + FK references to dimensions. Millions of rows, narrow columns.
Definition
Dimension Table: Describes context — who, what, where, when. Contains descriptive attributes. Thousands of rows, wide columns. Examples: DimDate, DimProduct, DimCustomer.

Measures: Additivity

MeasureAdditive across rows?Additive across time?Note
quantity✅ Yes✅ YesFully additive
gross_revenue_pkr✅ Yes✅ YesFully additive
net_revenue_pkr✅ Yes✅ YesFully additive
unit_price_pkr❌ No❌ NoNon-additive — use weighted avg
discount_pct❌ No❌ NoNon-additive — compute from additive parts
on_hand_qty (inventory)✅ across products⚠️ Semi-additiveDon't SUM across periods — use last snapshot

Natural Keys vs Surrogate Keys

Definition
Natural Key (Business Key): Identifier from source system — e.g., customer_code = "C0042". May change, may not be unique across multiple sources.
Definition
Surrogate Key: Meaningless integer generated by the warehouse — e.g., customer_key = 117. Never changes. Insulates DW from source changes. Required for versioning (SCD).

Why Surrogate Keys? (3 Reasons to Know)

  1. Source independence: Source can renumber business keys — surrogate stays stable in DW
  2. History/versioning: When a customer changes segment, a new surrogate key is issued; old facts keep the old key
  3. Multi-source integration: Two systems both using product_code "P100" for different products — surrogates disambiguate
Example

CampusCart Star Schema

Definition
Degenerate Dimension: A business identifier (like order_id) stored directly in the fact table with no separate dimension table. It has no descriptive attributes worth a full dimension.
Exam Tip
Grain first, always. Before any DDL, write: "One row in FactSales represents ___." This determines what FKs, measures, and key strategy you need. Changing grain mid-design means redesigning everything.

Key Takeaways

  • Design order: Business Process → Grain → Dimensions → Facts
  • Fact table = measures + FK surrogate keys (many rows, narrow)
  • Dimension table = descriptive context (fewer rows, wide)
  • Natural key = source identifier; Surrogate key = warehouse integer, never changes
  • Star schema: one fact + dimensions connecting directly — simple joins for BI tools
Practice Questions
Easy: What is the grain of a fact table and why must it be declared first?

Answer: The grain is a precise statement of what one row represents (e.g., "one order-line item"). It must be declared first because it determines which measures belong, which dimensions connect, and how many rows the table has. Changing the grain mid-design forces a complete redesign.

Medium: Why is unit_price_pkr non-additive? How do you compute a correct overall average price?

Answer: SUM(unit_price_pkr) across rows is meaningless — it adds selling prices for different products. Correct weighted average: SUM(net_revenue_pkr) / SUM(quantity). The numerator and denominator are both additive; dividing them gives the correct average price.

Hard: Two source systems both use customer_code "C100" for completely different customers. How does a surrogate key solve this?

Answer: The ETL tags source keys with their origin (e.g., "SysA-C100" vs "SysB-C100") before loading as business keys in the dimension. Each gets a unique surrogate (e.g., customer_key 412 and 873). The fact table stores only surrogates, so the two different "C100" customers are unambiguously separate — even though their raw business keys look identical.

7OLAP: ROLLUP, CUBE & Implementation Types

Lab 04 — Multidimensional analysis, hierarchical subtotals, ROLAP/MOLAP/HOLAP/DOLAP

OLAP provides multi-dimensional analysis — slicing data across time, products, and regions simultaneously. SQL extensions ROLLUP and CUBE generate subtotals automatically without writing multiple queries.

OLAP Implementation Types

TypeHow It WorksWhen To Use
ROLAPQueries run directly on relational fact + dimension tables. Flexible, scales to detail.Need flexibility and full detail access
MOLAPSummaries pre-computed and stored in a multidimensional cube. Fastest for standard queries.Fixed dimensions, maximum speed needed
HOLAPDetail stays relational (ROLAP); frequently-used summaries pre-computed (MOLAP). Best of both.Mix of standard reports + ad-hoc detail
DOLAPSmall analytical subset downloaded to desktop for local offline analysis.Travelling analysts, offline usage
Lab Context
ROLAP = querying the star schema tables directly. MOLAP is simulated by pre-aggregated summary tables (like lab03_report.monthly_region_category). HOLAP = both approaches coexist in the same system.

ROLLUP — Hierarchical Subtotals

ROLLUP(A, B, C) generates subtotals by progressively removing columns from the right: (A,B,C), (A,B), (A), () — the grand total. 4 levels for 3 dimensions.

Example

Product Hierarchy Rollup: Region → Category → Product

SELECT
    CASE WHEN GROUPING(r.region_name) = 1 THEN 'ALL REGIONS'
         ELSE r.region_name END  AS region,
    CASE WHEN GROUPING(p.category)    = 1 THEN 'ALL CATEGORIES'
         ELSE p.category END     AS category,
    CASE WHEN GROUPING(p.product_name)= 1 THEN 'ALL PRODUCTS'
         ELSE p.product_name END AS product,
    SUM(fs.net_revenue_pkr)      AS net_revenue
FROM   lab04.fact_sales fs
JOIN   lab04.dim_product p ON fs.product_id = p.product_id
JOIN   lab04.dim_region  r ON fs.region_id  = r.region_id
GROUP  BY ROLLUP(r.region_name, p.category, p.product_name)
ORDER  BY r.region_name NULLS LAST, p.category NULLS LAST;
-- Rows: product-level | category subtotals | region subtotals | grand total
Definition
GROUPING(column): Returns 1 when the column was removed by ROLLUP/CUBE (subtotal row), and 0 for normal detail rows. Use with CASE to replace NULL labels with "ALL REGIONS", etc.

Time Hierarchy Rollup

Example
SELECT d.year, d.quarter, d.month,
       SUM(fs.net_revenue_pkr) AS revenue
FROM   lab04.fact_sales fs
JOIN   lab04.dim_date d ON fs.date_key = d.date_key
GROUP  BY ROLLUP(d.year, d.quarter, d.month)
ORDER  BY d.year NULLS LAST, d.quarter NULLS LAST, d.month NULLS LAST;
-- Output: monthly detail → quarter subtotals → year subtotals → grand total

CUBE — All Combinations

CUBE(A, B, C) generates ALL possible subtotal combinations: 2³ = 8 grouping sets. Adding one dimension doubles the combinations.

Example

Two-Dimensional Cube: Region × Channel

SELECT
    COALESCE(r.region_name, 'ALL REGIONS') AS region,
    COALESCE(fs.channel,    'ALL CHANNELS') AS channel,
    SUM(fs.net_revenue_pkr)                AS revenue
FROM   lab04.fact_sales fs
JOIN   lab04.dim_region r ON fs.region_id = r.region_id
GROUP  BY CUBE(r.region_name, fs.channel)
ORDER  BY r.region_name NULLS LAST, fs.channel NULLS LAST;
-- Includes: Region+Channel detail | Region-only subtotals |
--           Channel-only subtotals | Grand total (both NULL)
Dimensions in CUBEGrouping Sets Generated
2 (A, B)2² = 4
3 (A, B, C)2³ = 8
4 (A, B, C, D)2⁴ = 16
Common Mistake — ROLLUP vs CUBE
ROLLUP follows one strict hierarchy (A → B → C → total) — use for time or product hierarchies. CUBE generates every possible combination — use when there's no natural hierarchy and you want all subtotals (region × channel × category).

Key Takeaways

  • ROLAP: query star directly | MOLAP: pre-computed cubes | HOLAP: both | DOLAP: local desktop
  • ROLLUP(A,B,C) → 4 subtotal levels: (A,B,C), (A,B), (A), () — hierarchical
  • CUBE(A,B,C) → 2³ = 8 grouping sets — all combinations
  • GROUPING(col) = 1 → subtotal row, = 0 → normal detail row
  • Adding one dimension to CUBE doubles the subtotal combinations
Practice Questions
Easy: What is the difference between ROLLUP and CUBE?

Answer: ROLLUP generates subtotals along a single hierarchy — progressively removing columns right to left (detail → subtotal → total). CUBE generates subtotals for ALL possible combinations of listed columns. ROLLUP is for hierarchies (Year-Quarter-Month); CUBE is for cross-dimensional analysis where every combination matters.

Medium: CUBE on (Region, Channel, Category) produces how many grouping sets?

Answer: 2³ = 8: (R,Ch,Cat), (R,Ch), (R,Cat), (Ch,Cat), (R), (Ch), (Cat), () = grand total.

Hard: Explain HOLAP and when you'd choose it over pure ROLAP.

Answer: HOLAP keeps detailed fact data in relational tables (ROLAP layer) for ad-hoc queries, while pre-computing frequently-used summaries in materialised aggregate tables (MOLAP layer). Choose HOLAP when: most user queries are repetitive and standard (use pre-computed tables for speed), but analysts occasionally need raw detail (use the relational star). Pure ROLAP is slower for repetitive queries; pure MOLAP can't answer unexpected detail-level questions.

Step 3 — Load Dimensions with Surrogates

Example
-- DimCustomer: SERIAL auto-generates surrogate, UNIQUE on business key
CREATE TABLE lab06_dw.dim_customer (
    customer_key     SERIAL PRIMARY KEY,       -- surrogate (auto-increment)
    customer_code    TEXT UNIQUE NOT NULL,     -- natural/business key (cleaned)
    customer_name    TEXT,
    customer_segment TEXT
);

-- Load: TRIM whitespace, standardise casing, DISTINCT to deduplicate
INSERT INTO lab06_dw.dim_customer (customer_code, customer_name, customer_segment)
SELECT DISTINCT
    TRIM(customer_code)             AS customer_code,
    INITCAP(TRIM(customer_name))    AS customer_name,
    INITCAP(TRIM(customer_segment)) AS customer_segment
FROM   lab06_stg.stg_customers
WHERE  customer_code IS NOT NULL;

-- Validate: no duplicate business keys in warehouse dim
SELECT customer_code, COUNT(*) FROM lab06_dw.dim_customer
GROUP BY 1 HAVING COUNT(*) > 1;  -- must return 0 rows

Step 4 — Generate Date Dimension

Example
CREATE TABLE lab06_dw.dim_date (
    date_key    INT PRIMARY KEY,   -- YYYYMMDD: 20250315
    full_date   DATE,
    day         INT,
    month       INT,
    month_name  TEXT,
    quarter     INT,
    year        INT,
    day_of_week TEXT
);

INSERT INTO lab06_dw.dim_date
SELECT TO_CHAR(d, 'YYYYMMDD')::INT  AS date_key,
       d                             AS full_date,
       EXTRACT(DAY     FROM d)::INT  AS day,
       EXTRACT(MONTH   FROM d)::INT  AS month,
       TO_CHAR(d, 'Month')           AS month_name,
       EXTRACT(QUARTER FROM d)::INT  AS quarter,
       EXTRACT(YEAR    FROM d)::INT  AS year,
       TO_CHAR(d, 'Day')             AS day_of_week
FROM   GENERATE_SERIES('2024-01-01'::DATE, '2026-12-31'::DATE, '1 day') AS d;
-- Never insert dates manually — use GENERATE_SERIES

Step 5 — Create & Load Fact Table (Surrogate-Key Mapping)

Example
CREATE TABLE lab06_dw.fact_sales (
    line_id              INT PRIMARY KEY,  -- natural grain key
    order_id             INT,              -- degenerate dimension
    date_key             INT REFERENCES lab06_dw.dim_date(date_key),
    customer_key         INT REFERENCES lab06_dw.dim_customer(customer_key),
    product_key          INT REFERENCES lab06_dw.dim_product(product_key),
    region_key           INT REFERENCES lab06_dw.dim_region(region_key),
    channel_key          INT REFERENCES lab06_dw.dim_channel(channel_key),
    quantity             INT,
    unit_price_pkr       NUMERIC(12,2),
    discount_pct         INT,
    gross_revenue_pkr    NUMERIC(14,2),
    discount_amount_pkr  NUMERIC(14,2),
    net_revenue_pkr      NUMERIC(14,2)
);

-- Surrogate-key mapping: JOIN staging tables to dimensions
INSERT INTO lab06_dw.fact_sales
SELECT
    oi.line_id,
    oi.order_id,
    TO_CHAR(o.order_date, 'YYYYMMDD')::INT AS date_key,
    dc.customer_key,   -- resolved: customer_code → customer_key
    dp.product_key,    -- resolved: product_code  → product_key
    dr.region_key,     -- resolved: region_code   → region_key
    dch.channel_key,
    oi.quantity, oi.unit_price_pkr, oi.discount_pct,
    oi.gross_revenue_pkr, oi.discount_amount_pkr, oi.net_revenue_pkr
FROM   lab06_stg.stg_order_items oi
JOIN   lab06_stg.stg_orders      o   ON oi.order_id        = o.order_id
JOIN   lab06_dw.dim_customer     dc  ON TRIM(o.customer_code)= dc.customer_code
JOIN   lab06_dw.dim_product      dp  ON TRIM(oi.product_code) = dp.product_code
JOIN   lab06_dw.dim_region       dr  ON TRIM(o.region_code)   = dr.region_code
JOIN   lab06_dw.dim_channel      dch ON TRIM(o.channel)       = dch.channel_name;
-- The fact table stores surrogate integers only — never raw codes

Step 6 — Validate Everything

Example
-- 1. Row count: staging vs fact must match
SELECT COUNT(*) FROM lab06_stg.stg_order_items;   -- source
SELECT COUNT(*) FROM lab06_dw.fact_sales;          -- warehouse

-- 2. Orphan checks (all must return 0 rows)
SELECT COUNT(*) FROM lab06_dw.fact_sales fs
LEFT JOIN lab06_dw.dim_customer dc ON fs.customer_key = dc.customer_key
WHERE dc.customer_key IS NULL;

-- 3. Measure reconciliation (must match exactly)
SELECT SUM(net_revenue_pkr) FROM lab06_stg.stg_order_items;
SELECT SUM(net_revenue_pkr) FROM lab06_dw.fact_sales;

-- 4. Constraint test: prove FK protection works
INSERT INTO lab06_dw.fact_sales (line_id, customer_key, ...)
VALUES (99999, 99999, ...);  -- customer_key 99999 doesn't exist → FK error!

Common Load Failures

SymptomRoot CauseDiagnostic
DW has MORE rows than sourceDimension has duplicate business keys → many-to-many join during mappingCheck dim for duplicate business keys
DW revenue > source revenueFact rows duplicated (bad join or double-load)Compare row counts staging vs fact
DW has FEWER rows than sourceOrphan source rows dropped (INNER JOIN misses records)Use LEFT JOIN in fact load; check NULLs on dim side

Critical Rule
Row-count reconciliation alone is insufficient. You must also verify measure reconciliation (SUM revenues match). A fact table can have the correct row count but wrong revenue if a mapping error caused incorrect surrogate resolution.

Key Takeaways

  • Pipeline: Source CSVs → Staging (raw) → DW Dimensions (cleaned+surrogates) → Fact (surrogate FKs only)
  • Data quality: NULL keys, duplicate keys, row count, orphan FKs, whitespace/casing
  • Surrogate-key mapping: fact INSERT must JOIN staging to each dimension to swap business key → surrogate
  • Date dimension: generate with GENERATE_SERIES() — never insert manually
  • Validation = row-count match + measure reconciliation + zero orphans + constraint tests
Practice Questions
Easy: What is the purpose of a staging schema in a DW pipeline?

Answer: Staging is a landing zone for raw source data, preserved as-is without transformation. It enables: (1) data quality profiling before loading, (2) audit trail for reconciliation (compare staging vs DW at any time), and (3) decoupling source system loads from warehouse transformations. Clean only when loading dimensions and facts, not in staging.

Medium: Fact table has 3,500 rows but source staging has only 3,469. Most likely cause?

Answer: A dimension table has duplicate business keys. When the fact load JOINs staging to the dimension on the business key, one source row matches multiple dimension rows → one source row produces multiple fact rows (fan-out). Fix: ensure each dimension business key is unique (HAVING COUNT(*) > 1 must return nothing) before loading facts.

Hard: Describe the full surrogate-key mapping flow from a source order_item row to a fact_sales row.

Answer: (1) Staging: stg_order_items has raw codes: customer_code='C042', product_code='P018'. (2) ETL JOINs stg_order_items to stg_orders to get order context (customer_code, order_date, region_code). (3) JOINs to dim_customer on customer_code='C042' → resolves customer_key=117. (4) JOINs to dim_product on product_code='P018' → resolves product_key=36. (5) JOINs to dim_date on formatted date → date_key=20250315. (6) Inserts fact row: line_id, order_id, date_key=20250315, customer_key=117, product_key=36, + measures. The fact table never stores 'C042' or 'P018' — only surrogate integers.
